# 第三阶段收尾：Firebase 服务端写入配额

## 结论

第三阶段已实现基于 Firestore Security Rules 的 UID 级服务端写入配额。配额不是客户端计数器：每次真实快照写入都必须与配额文档在同一原子 Firestore commit 中更新，规则使用 `getAfter()` 和服务器时间验证这两项写入。直接写账号文档或单独修改配额文档均被拒绝。

## 服务端限制

| 范围 | 限制 | 规则 |
|---|---:|---|
| 单 UID 写入频率 | 每 5 秒最多 1 次 | 依据 `request.time` 与上次 `lastWriteAt` |
| 单 UID 写入次数 | 每个固定 24 小时窗口最多 100 次 | 仅实际改变快照的原子提交扣额度 |
| 单 UID 注册的 ChatGPT 账号快照 | 最多 20 个 | 配额文档维护不可由客户端删除的账号哈希注册表 |
| 单个账号快照 | 240,000 字节 | 保留原有 Firestore 文档大小规则 |

固定 24 小时窗口从第一次成功写入时开始，只有服务器确认 24 小时已经过去才允许重置。每次写入会同时改变一个账号快照和一个 UID 配额文档；两者要么一起成功，要么一起失败。无变化同步不消耗写入额度。

## 实现内容

- `firestore.rules`：增加 `users/{uid}/usage/cloudWrites` 配额文档；账号写入要求配额文档在同一 commit 中更新，配额写入要求对应账号快照在同一 commit 中发生实际变化。
- Security Rules 校验 Firebase UID、邮箱验证、账号哈希、配额字段结构、服务器时间戳、5 秒间隔、100 次24 小时固定窗口限额、20 个账号注册上限和原有 240 KB 快照上限。
- 客户端同步改为 Firestore `documents:commit`，对账号快照和配额文档使用更新时间前提，避免并发设备丢失配额增量。
- 客户端严格校验读取到的配额文档；损坏或超限的配额状态失败关闭。
- 配额拒绝、冲突或网络失败时，不应用云端合并、不前移本地同步基线，也不清除本地数据。
- 配额限制按 Firebase UID 共享；同一 UID 的不同 ChatGPT 账号共用写入冷却和每日额度。
- 不引入 Cloud Functions、服务账号密钥或 Blaze 付费依赖。

## 已知边界

- 配额按 Firebase UID 计算，不跨多个 Firebase UID 合并。该方案不是跨身份的全局反滥用服务。
- 升级前已有的账号文档在下一次成功写入时惰性加入注册表；未注册文档仍可读取，但需要注册名额才能继续写入。
- 配额文档本身会增加每次同步的 Firestore 读写成本，发布前必须核算 Spark 用量。
- 新客户端与新版 `firestore.rules` 必须作为同一版本发布。规则部署后，升级前客户端的单文档 PATCH 会被拒绝；不能提前只部署规则或客户端。
