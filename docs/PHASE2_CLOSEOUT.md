# 第二阶段收尾：跨设备删除状态与保留策略

## 结论

第二阶段的 V1 收尾采用**持久保留 + 容量上限 + 超限失败关闭**，不执行时间清理或自动压缩。原因是当前同步协议没有云端设备注册表，也没有每台设备对删除代次的确认水位。无法证明某台长期离线的旧设备已经收到删除标记；提前移除标记会允许旧设备重新上传已删除的提示词或目录别名。

## 已具备的保护

- 提示词删除标记按 ChatGPT 账号隔离并持久保存；重新使用已删除 ID 会被拒绝。
- 会话删除和最后一个目录别名删除使用不同的持久删除围栏，并保存账号归属。
- 云同步采用本地基线、当前本地数据和远端快照三方合并；旧快照的遗漏会被补成删除标记。
- 删除与同一条目的并发编辑会失败关闭；其他账号的数据和删除标记不会被当前账号清除。
- 本地别名清理要求用户预览后确认，并校验预览数据未发生变化。

## 本次收尾修改

- 将云端每类删除标记上限显式定义为 `CLOUD_MAX_TOMBSTONES_PER_KIND = 20,000`。
- 保留完整快照 `CLOUD_MAX_BYTES = 240,000` 的字节上限。
- 为三类云端删除标记增加 20,000 条边界、20,001 条拒绝、整体 240 KB 超限测试。
- 增加重复无操作合并后仍保留会话、别名和提示词删除标记的测试。
- 增加本地提示词删除标记 20,000 条边界测试；第 20,001 条删除请求被拒绝且原提示词和既有标记保持不变。
- 增加已存储的超限删除标记映射失败关闭测试，确保不会重写提示词数据。
- 在同步文档和发布清单中明确禁止 V1 自动清理删除标记。

## 当前容量边界

| 范围 | 上限 | 超限行为 |
|---|---:|---|
| 云端 deletedRoutes | 20,000 条 | 拒绝快照 |
| 云端 deletedAliases | 20,000 条 | 拒绝快照 |
| 云端 deletedPrompts | 20,000 条 | 拒绝快照 |
| 单份云端快照 | 240,000 字节 | 拒绝同步 |
| 本地每账号提示词删除标记 | 20,000 条 | 拒绝新增删除，不移除原数据 |

## 不在本阶段执行的操作

- 不按天数或最后活跃时间删除标记。
- 不清理生产 Firestore。
- 不重置 V1 云端快照。
- 不清空用户本地数据。
- 不改变 Firebase Authentication 账号。
- 不合并到 `main`，不发布 1.0.0。

## 未来安全压缩的前置条件

必须先实现云端设备注册、同步代次、每设备确认水位，以及旧设备撤销/过期策略。只有当所有仍获授权的设备都确认某一删除代次后，才允许回收该代次以前的标记。旧客户端必须被强制重新拉取完整快照，不能在缺少确认状态时继续写入。

## 下一阶段准入

本阶段代码收尾在以下条件满足后关闭：

1. 本分支 Pull Request 的 CI 通过类型检查、完整 Vitest、构建和浏览器 E2E。
2. 新增的边界与失败关闭测试通过。
3. 变更只合入 `rebuild/lunatoc-1.0.0`，不直接合入 `main`。

满足以上条件后，可以开始第三阶段 Firebase 服务端写入配额和频率限制。V1 删除标记压缩仍然延期，不构成第三阶段开发的前置条件。
